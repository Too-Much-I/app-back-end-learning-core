# 토선생 개발 9월 회고 — 출시 이후의 흐름을 다듬다

8월에는 앱을 출시하고 처음으로 사용자가 들어오는 모습을 봤다. 9월에는 그다음 흐름을 다듬는 작업이 이어졌다. 기존 사용자가 계속 서비스를 이용할 수 있도록 계정과 기록을 연결하고, 처리가 중간에 실패했을 때 다시 진행할 수 있는 방법을 보완했다.

Learning Core와 Identity를 중심으로 작업하면서 10초 챌린지도 추가했다. 새 기능을 구현하는 것과 함께, 여러 기능을 연결하고 실제 배포 환경에서 확인하는 데 시간을 썼다.

## 기존 계정에서는 정상인데, 신규 사용자는 멈췄다

출시 이후에는 테스트할 때와 다른 조건에서 문제가 드러나기도 했다. 팀에서 정리한 9월 초 장애 사례 중 하나는 신규 사용자가 시험 도중 같은 지점에서 멈추는 문제였다.

기존 계정으로 테스트했을 때는 정상적으로 진행됐지만, 신규 사용자 조건으로 다시 확인하자 특정 시험지의 음성이 로드되지 않는 문제가 재현됐다. 콘텐츠를 정리하면서 S3 파일을 복사하는 대신 이동해 해당 시험지의 음성 파일이 없어진 것이 원인이었다. 기존 계정은 다른 시험지를 사용하고 있어서 문제를 놓쳤다.

이 사례는 시험 API가 정상적으로 응답하는 것과 사용자가 실제로 시험을 끝까지 진행할 수 있는 것이 다르다는 점을 보여줬다. 계정과 배정된 시험지, 각 문항에서 사용하는 파일까지 조건을 맞춰서 확인해야 했다.

출시 전에는 정상적으로 동작하는 흐름을 확인하는 데 집중했다면, 출시 이후에는 ‘어떤 사용자가 어떤 조건에서 실패하는가’를 구체적으로 봐야 한다는 생각이 들었다.

## Identity: 기존 사용자가 다시 돌아올 수 있도록

Identity에서는 기존 Guest의 접근을 복구하는 hotfix와 가입을 중단했다가 다시 이어갈 수 있는 흐름을 작업했다. 새 계정을 만드는 것으로 문제를 우회하면 기존 학습 기록과의 연결이 달라질 수 있어, 같은 사용자와 기록을 유지하는 방향이 중요했다.

회원 전환 도중 앱을 종료하거나 가입을 끝내지 못한 경우도 고려했다. 다시 돌아왔을 때 기존 가입 과정을 이어갈 수 있는지, 유효기간이 지나 새로 준비해야 하는지, 아직 어떤 정보와 동의가 필요한지를 서버에서 명확하게 전달하도록 보완했다.

Refresh Token 재발급에서는 응답 유실을 다뤘다. 서버에서는 기존 Token을 교체하고 새 Token을 만들었는데, 앱이 응답을 받지 못할 수 있다. 이때 같은 요청을 다시 보냈다는 이유만으로 잘못된 Token 재사용으로 판단하면 정상 사용자도 접근에 문제가 생길 수 있었다.

같은 재발급 요청에는 제한된 기간 동안 처음 발급한 결과를 다시 받을 수 있도록 복구 처리를 구현했다. 다만 그사이에 로그아웃이나 탈퇴, 계정 변경이 있었다면 과거 응답으로 인증을 되살리지 않도록 현재 상태를 먼저 확인해야 했다.

이 밖에도 전체 로그아웃과 Firebase revoke, SNS 연결·해제, 선택 동의 처리를 보완했다. 로그인에 성공하는 순간뿐 아니라 통신이 끊기거나 가입이 중단된 이후의 흐름까지 다루는 작업이 많았다.

## 새 정책과 기존 사용자 사이에서

업데이트를 준비하면서 프론트엔드 팀원과 기존 사용자의 전환 방식에 의견 차이가 있었다. 인증 요청에서 같은 작업의 재시도를 구분하기 위한 값을 필수로 받도록 변경하려고 했는데, 이미 배포된 구버전 앱은 이 값을 보낼 수 없었다. 그대로 적용하면 기존 사용자는 인증 과정에서 오류를 겪게 되고, 당시 앱에는 강제 업데이트 기능도 없었다.

팀원은 기존 사용자가 오류 없이 계속 이용할 수 있도록 해당 값을 필수로 두지 말자고 제안했다. 나는 향후 유료화와 새로운 이용 정책을 준비하는 상황에서 구버전의 무료 이용을 계속 유지하면 전환 기준을 적용하기 어렵다고 생각했다.

하지만 사용자가 업데이트가 필요하다는 안내도 받지 못한 채 오류부터 겪게 된다는 우려에는 공감했다. 백엔드에서는 새 요청 계약과 정책 적용을 보고 있었고, 프론트엔드에서는 지금 앱을 사용하는 사람이 겪을 상황을 보고 있었다. 두 관점을 함께 고려해야 했다.

그래서 업데이트 안내와 유예기간을 두고 전환하는 방식을 제안했다. 구·신버전 서버를 나누고, 웹뷰의 피드백 페이지에 들어가기 전에 업데이트 안내를 보여주는 방향으로 정리했다. 우선 1주의 유예기간을 두고 사용자 수를 보며 조정하고, 업데이트 필요 여부를 응답값으로 전달하는 방안도 공유했다.

이 논의를 통해 서버의 변경 시점을 정하는 것뿐 아니라, 사용자가 변경을 알고 준비할 수 있는 경로까지 함께 설계해야 한다는 점을 배웠다. 특히 이미 배포된 앱이 있는 상태에서는 앞으로 사용할 계약만큼 기존 앱이 할 수 있는 것과 할 수 없는 것도 중요했다.

협업에서도 내 판단의 근거를 설명하는 데서 끝내지 않고, 상대가 우려하는 부분을 실제 대안에 반영해야 했다. 이번에는 새로운 정책을 적용하려는 이유와 기존 사용자의 경험을 보호하려는 이유를 함께 담으면서 전환 방향을 정리할 수 있었다.

## Learning Core: 계정과 기록, 실패와 복구를 연결하기

8월에 Identity에서 Guest 승격과 계정 통합의 기반을 만들었다면, 9월에는 Learning Core의 학습 기록을 연결하는 구현으로 이어졌다.

계정 통합 이벤트를 받으면 시험과 문항 결과, 종합 피드백의 소유권을 옮기도록 했다. 이 과정에서 통합 이전 계정의 Token이 새로운 소유자의 데이터를 조회하지 못하도록 접근 경계도 함께 처리했다.

기록 이전은 userId를 일괄 변경하는 것만으로 끝나지 않았다. 채점 Callback이나 시험 생성이 동시에 진행될 수 있기 때문에, 이전 중인 소유권과 다른 작업이 어긋나지 않도록 같은 Transaction 경계를 사용해야 했다.

시험 생성의 자동 복구도 추가했다. Billing에 응시권을 예약하고 Learning Core에 시험을 저장하는 과정 중 하나가 성공한 뒤 응답만 유실되거나, 다음 단계로 넘어가지 못할 수 있었다. 사용자가 다시 요청할 때만 복구하는 흐름에서 나아가, 저장된 작업을 worker가 확인하고 이어서 처리하도록 구현했다.

여기서 중요한 점은 timeout을 곧바로 실패로 확정하지 않는 것이었다. 응답을 못 받았어도 상대 서버에서는 처리가 끝났을 수 있다. 현재 상태를 먼저 조회하고, 확인된 근거를 기준으로 확정하거나 취소하도록 했다.

채점 결과와 시험 상태를 Billing에 전달하는 outbox도 구현했다. 내부 결과 저장과 전달할 이벤트를 함께 남기고, 전송이 실패하면 같은 이벤트를 다시 보내는 방식이다. 서버가 나뉘어 있을수록 한 번의 요청 성공보다, 중간에 끊긴 뒤 어떻게 이어갈지가 중요해졌다.

## 새로운 학습 흐름과 실제 배포에서 드러난 문제

9월에는 긴 모의고사와 별도로 10초 챌린지를 구현했다. 짧은 음성 답변을 제출하고 AI 채점 결과를 확인하는 흐름이다. 기존 시험과 별도 영역으로 구성하면서 문제 제공, 업로드, 제출, 결과와 이력을 연결했다.

짧은 기능이라고 처리해야 할 상태까지 단순한 것은 아니었다. 제출 유효시간이 지나거나 AI 응답이 늦게 도착할 수 있고, 중복 Callback이 들어올 수도 있었다. 무음 결과와 기술적인 실패의 의미도 구분해야 했다.

기능을 연결한 뒤에는 실제 배포에서 다른 문제가 드러났다. 월말 테스트 서버 배포 과정에서 Mongo 인덱스 검증과 Repository 등록 문제를 수정했다. 계정 통합과 챌린지를 함께 활성화했을 때는 여러 Clock bean 때문에 의존성 주입이 실패했고, 공용 UTC Clock을 사용하도록 정리했다.

기동 중 헬스체크의 유예시간이 부족한 문제도 있었다. 같은 이미지라도 충분한 기동 시간을 확보한 뒤 정상 상태로 전환되는 것을 확인했다. 코드가 실행될 수 있는지와 배포 시스템이 정상 기동으로 판단하는지를 함께 봐야 했다.

이 과정을 거치며 개별 기능의 테스트 통과와 여러 기능을 함께 켠 애플리케이션의 기동 성공은 별도로 검증해야 한다는 점을 배웠다. 9월 말에는 테스트 서버의 기동과 인증 연결을 확인했고, 실제 모바일 학습과 회원 통합의 전체 검증은 다음 단계로 남겨뒀다.

## 9월을 지나며

Billing에서도 계정 통합과 재가입에 따른 무료권 소유 관계, 중단 시험의 승계, 무료 이용권 조회를 보완했다. 각 서버의 기능이 늘어날수록 사용자 계정과 학습 기록, 응시권이 서로 일관되게 연결되는지가 중요했다.

8월에는 사용자가 약 20분 동안 들인 노력이 점수와 피드백으로 이어져야 한다고 생각했다. 9월에는 그 고민이 계정 전환과 응답 유실, 시험 생성의 자동 복구까지 확장됐다.

기존 사용자 전환을 논의하면서는 기술적인 변경과 그 변경을 안내하는 과정이 함께 필요하다는 점도 배웠다. 다음 업데이트에서는 서버와 앱의 계약뿐 아니라 사용자 안내와 전환 일정까지 더 일찍 팀원과 맞춰보고 싶다.

새 기능을 추가하면서도 기존 사용자가 돌아올 수 있고, 이미 쌓은 기록이 이어지며, 중간 실패를 다시 진행할 수 있도록 만드는 것. 9월에는 그런 흐름을 구현하고 검증하는 데 많은 시간을 썼다. 다음에는 실제 모바일과 서버를 연결한 전체 흐름까지 확인하면서 남은 부분을 다듬어가려고 한다.
