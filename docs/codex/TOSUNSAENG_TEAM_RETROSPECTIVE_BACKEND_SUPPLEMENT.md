- 연결 문서: [포트폴리오 전체 목록](TOSUNSAENG_PORTFOLIO_CONTENT_INVENTORY.md), [트러블슈팅 사례집](TOSUNSAENG_TROUBLESHOOTING_CASEBOOK.md).

## 1. 5줄 결론

1. **[회고 사실]** 피드백 생성 실패로 사용자가 약 10분 기다리다 이탈한 실제 사례가 있다. 백엔드의 상태 관리·제한된 재시도·선택적 복구를 설명하는 배경으로 적합하다. [7월 회고](https://velog.io/@jinjinjara1022/아이디어에서-첫-사용자까지-토선생-개발-7월-회고), [복구 서비스](../../src/main/java/web/tosunsaeng/domain/exams/application/ExamGradingService.java).
2. **[회고 사실]** MockExam1의 S3 음성 이동으로 신규 사용자가 Q5를 진행하지 못한 장애가 있다. 계정뿐 아니라 배정 시험지까지 맞춰 재현해야 한다는 운영 소재다. [장애 회고](https://velog.io/@jinjinjara1022/토선생-개발-일지-01-멈춰버린-서비스), [시험지 선택](../../src/main/java/web/tosunsaeng/domain/exams/application/ExamSessionManager.java:291).
3. **[구현 확인·추론]** AI 필드 단위 repair와 백엔드 문항·Summary 단위 복구는 서로 다른 책임이다. 두 계층의 재시도 범위·한계를 설명하면 단순한 “재시도 추가”보다 좋은 소재가 된다. [8월 회고](https://velog.io/@jinjinjara1022/일단-되게에서-제대로-되게로-토선생-개발-8월-회고), [복구 계획](FEEDBACK_GENERATION_RECOVERY_PLAN.md).
4. **[구현 확인]** 무음과 기술적 실패를 구분하는 후속 사례는 10초 챌린지에 있다. 이를 과거 모의고사 장애의 직접 수정이라고 쓰면 안 된다. [Callback 파서](../../src/main/java/web/tosunsaeng/domain/challenge/ChallengeCallback.java), [결과 처리](../../src/main/java/web/tosunsaeng/domain/challenge/ChallengeCallbackService.java).
5. **[권장]** 아래 9개 소재 중 본인 역할이 확인되는 것을 고르고, AI 품질 개선은 팀원 성과로 표시한다. 서비스 성과 수치는 앱·웹과 시점을 명시한다. [전체 표·수치 정의](#6-부록-상세-조사-근거와-전체-표).

## 2. 내가 반드시 읽어야 하는 내용

가장 추천하는 조합은 **① 10분 대기 이탈 → 실패 상태와 복구 설계**, **② 특정 시험지 음성 누락 → 사용자 조건을 맞춘 장애 재현**, **③ AI·백엔드의 재시도 책임 분리**다.

①은 이미 존재하는 백엔드 구현과 연결하기 쉽다. ②는 운영 현상과 원인이 구체적이지만 본인이 어떤 진단·복구를 맡았는지 추가 확인이 필요하다. ③은 기존 사례집 TS-01·02·03의 설명을 보강하는 소재이지 별도 장애 3건을 뜻하지 않는다.

팀원은 글에서 AI 평가·피드백 생성을 담당했다고 밝혔다. 따라서 “STT를 개선했다”, “AI repair를 구현했다”, “모델 비용을 절감했다”를 사용자 개인 성과로 바꾸지 않는다. 본인 역할을 확인한 뒤 **“AI 담당자와 계약을 맞추고 백엔드의 저장·상태·복구 경로를 구현·검증했다”**처럼 작성한다. [7월 회고](https://velog.io/@jinjinjara1022/아이디어에서-첫-사용자까지-토선생-개발-7월-회고).

## 3. 내가 결정해야 하는 사항

- **S3 장애 기여:** 누가 누락을 발견했고, 본인은 파일 복구·경로 수정·재현·검증 중 무엇을 맡았는가? 확인 전에는 팀 운영 사례로만 사용한다.
- **10분 대기 사건과 개선의 연결:** 현재 Job·retry 구현이 그 사건 직후의 직접 조치였는지, 이후 별도 개선이었는지 당시 작업 기록으로 확정한다.
- **공개 범위:** 팀원 회고는 링크로 출처를 밝히고, 실제 사용자의 음성·답변·계정·원본 로그는 포트폴리오에 싣지 않는다.
- **성과 지표:** 본문에는 완료율·대기시간·복구 성공률처럼 본인이 설명 가능한 측정값을 우선한다. 글의 과거 수치 외에 전후 개선율을 임의로 채우지 않는다.

## 4. 주요 위험과 미확인 사항

- 팀원 회고의 장애·사용량은 외부 서술 근거다. 운영 DB·S3·모바일 로그로 독립 검증하지 않았다.
- S3 장애 글에는 파일 복구 방법·복구 후 전체 응시 성공·정확한 HTTP 오류 코드가 명시되지 않았다. “404를 고쳐 복구했다”, “재발 방지 자동화를 완료했다”는 아직 쓸 수 없다.
- 7월 AI repair 반복 실패를 사용자가 설명한 **동기 호출에 따른 백엔드 스레드 고갈**과 동일 사건으로 단정하지 않는다. 서로 다른 원인일 수 있으며 글에는 thread dump·pool 수치가 없다.
- 현재 시험지 선택·URL 생성 코드는 장애가 백엔드와 연결되는 구조를 설명할 뿐, 9월 2일 당시 배포 코드를 그대로 재현하는 증거가 아니다.
- 8월의 무음 차단은 AI 담당자의 모의고사 개선이다. 9월의 Challenge `no_speech`는 별도 계약·기능이며 운영 활성화도 별도다.
- AI 모델 비교는 제한된 실험이다. “100개 중 98개 판단 일치”는 **정확도 98%**나 동등 성능의 증명이 아니다. 글의 모델 표기와 실제 model ID·버전은 대조하지 않았다.
- 골든 데이터셋 구축은 8월 회고에서 9월 계획으로 제시됐다. 완성된 평가 자동화나 운영 모델 전환으로 적지 않는다.

## 5. 현재 작업과 직접 관련된 설명

### 5.1 약 10분 대기 후 이탈: 재시도 자체가 장애를 늘릴 수 있다 — TS-24

**[회고 사실] 문제·원인:** 모델 교체 후 출력 언어·형식 문제가 반복됐고, 복구도 반복되면서 처리 시간이 길어지거나 전체 작업이 실패했다. 실제 사용자 한 명이 피드백 생성 실패로 약 10분 기다린 뒤 결과 없이 이탈했다. 글은 최대 재시도·최종 실패·사용자 상태 전달의 필요성을 설명한다. [7월 회고](https://velog.io/@jinjinjara1022/아이디어에서-첫-사용자까지-토선생-개발-7월-회고).

**[구현 확인] 연결되는 백엔드:** 문항·Summary Job을 구분하며 완료 결과는 재전송하지 않고 실패·timeout 대상을 복구한다. 기본 설정은 PENDING 1분, PROCESSING 3분, 최대 dispatch 3회이며 환경 설정으로 달라진다. 빈 Summary는 `FEEDBACK_GENERATION_FAILED`로 취급하고 사용자 요청 시 Summary 재생성 세대를 올린다. 이 세대 증가는 같은 요청의 전송 재시도와 다르다. [서비스](../../src/main/java/web/tosunsaeng/domain/exams/application/ExamGradingService.java), [설정](../../src/main/resources/application.yml:56), [테스트](../../src/test/java/web/tosunsaeng/domain/exams/application/ExamGradingServiceTest.java).

**[추론] 설명 가치:** “에러가 나면 다시 호출”이 아니라 **완료·진행 중·실패·미제출을 구분하고 복구 범위를 결정**하는 백엔드 경험이다. 다만 위 timeout을 합산해 전체 사용자 대기시간 상한이라고 주장하면 안 된다. 사용자 재요청과 AI 내부 repair를 포함한 전체 예산은 별도 문제다.

**문장 후보:** “팀 운영 중 AI 피드백 생성이 반복 실패해 사용자가 장시간 대기 후 이탈한 사례가 있었습니다. 백엔드에서는 문항·종합 피드백 작업의 상태와 재전송 횟수를 관리하고, 완료 결과를 유지한 채 실패 범위만 복구하는 경로를 마련했습니다.” 본인 역할·시점 확인 후 사용한다. 기존 상세 수정은 사례집 TS-01·02·03을 참조한다.

### 5.2 특정 시험지의 S3 음성 누락: 신규 사용자 조건으로 재현 — TS-23

**[회고 사실] 현상:** 첫날 4명, 다음 날 5명이 Q4 이후 멈췄다. 기존 테스트 계정으로는 정상 완료했지만 계정을 초기화해 신규 사용자 조건으로 시도하자 Q5 음성이 로드되지 않았다.

**[회고 사실] 원인:** 웹 체험 콘텐츠와 모의고사 1번을 정리하는 과정에서 S3 파일을 복사하지 않고 이동해 MockExam1이 사용하던 음성이 없어졌다. 정상 테스트는 다른 시험지를 사용하고 있어 장애를 놓쳤다. [장애 회고](https://velog.io/@jinjinjara1022/토선생-개발-일지-01-멈춰버린-서비스).

**[구현 확인] 연결되는 백엔드:** 현재는 완료 횟수가 적은 시험지를 우선하고 동률이면 sequence 순으로 선택한다. 문항 음성 Key는 `questions/{mockExamId}/q_{questionNumber}.wav`, Part 3 안내는 `questions/{mockExamId}/part3_intro.wav`로 생성한다. 해당 Presigned GET 발급 메서드는 Object 존재 여부를 확인하지 않는다. 현재 catalog 검사는 ID·sequence·활성 여부·문항 존재 등을 검사하지만 이 경로에서 S3 음성 존재와 재생 가능성을 검증하지는 않는다. [시험지 선택](../../src/main/java/web/tosunsaeng/domain/exams/application/ExamSessionManager.java:291), [Key·URL 생성](../../src/main/java/web/tosunsaeng/domain/exams/application/ExamServiceImpl.java:77), [catalog](../../src/main/java/web/tosunsaeng/domain/exams/application/MockExamCatalogService.java).

**[추론] 핵심 교훈:** 백엔드 API가 URL을 정상 반환하는 것만으로 시험 진행 성공을 보장할 수 없다. 재현 조건에는 앱 버전·계정뿐 아니라 **배정 시험지·문항·참조 리소스**가 포함돼야 한다. 공유 자원을 사용하는 서비스는 서버를 분리했어도 콘텐츠 변경으로 함께 영향을 받을 수 있다.

**[제안·미구현] 재발 방지:** 배포 대상 시험지의 필수 파일 manifest와 존재/접근성 검사, 신규 사용자 첫 배정·기존 사용자 다른 배정의 전체 응시 smoke, “복사 → 새 참조 검증 → 전환 → 기존 참조 소멸 확인 후 정리” 절차를 후보로 둔다. HeadObject만으로 실제 음성 재생을 보장하지 못하므로 모바일 재생 검증도 필요하다. 이번에는 운영 파일·웹 저장소를 조회하거나 수정하지 않았다.

**문장 후보:** “팀 서비스에서 신규 사용자가 같은 문항에서 멈추는 현상을 조사한 결과, 기존 계정과 다른 시험지가 배정되고 해당 시험지의 S3 음성이 이동된 사실이 확인됐습니다. 이 사례를 통해 API 정상 응답뿐 아니라 시험지별 콘텐츠 참조와 신규 사용자 경로를 검증해야 한다는 점을 확인했습니다.” 본인이 조사에 참여하지 않았다면 “팀의 장애 사례를 분석하면서”로 바꾼다. 복구 성과는 추가 근거가 필요하다.

### 5.3 AI repair와 백엔드 복구를 구분한 다층 재시도

**[회고 사실]** AI 담당자는 누락·형식 오류가 있는 피드백을 전체 재생성하던 방식에서, 잘못된 필드만 필요한 맥락과 함께 다시 생성하는 방식으로 개선했다고 밝혔다. [8월 회고](https://velog.io/@jinjinjara1022/일단-되게에서-제대로-되게로-토선생-개발-8월-회고).

**[구현 확인]** 백엔드는 AI 내부 필드를 직접 repair하지 않는다. 문항 결과가 있으면 해당 채점을 건너뛰고, 필요한 경우 Summary만 재생성한다. 이전 Summary 세대 Callback이 새 결과를 덮지 않게 구분한다. [복구 서비스](../../src/main/java/web/tosunsaeng/domain/exams/application/ExamGradingService.java), [복구 계약](FEEDBACK_GENERATION_RECOVERY_PLAN.md).

**[추론·제안]** 면접에서는 “AI는 결과 내부의 유효성, 백엔드는 작업의 접수·완료·재전송·중복을 책임진다”고 설명할 수 있다. 백엔드 재전송과 AI 내부 repair가 겹치면 비용·시간이 증폭될 수 있으므로 계층별 횟수뿐 아니라 전체 시간 예산·멱등 키·최종 실패 합의도 중요하다. 전체 예산이 시험 전 구간에서 이미 구현됐다는 뜻은 아니다.

### 5.4 무음 환각: 답변 없음과 서버 실패를 분리

**[회고 사실]** 말하지 않은 음성이나 잡음에서 STT가 문장을 만들어 냈고 불필요한 채점·repair까지 이어졌다. AI 담당자는 음성 길이와 정규화한 STT 결과를 이용한 사전 guard를 설명한다. Part 2의 walk/work 오인식은 이미지 객체·행동 metadata를 STT keyword로 넣는 별도 개선이다. 두 작업 모두 AI 담당자 성과다. [8월 회고](https://velog.io/@jinjinjara1022/일단-되게에서-제대로-되게로-토선생-개발-8월-회고).

**[구현 확인]** 현재 10초 챌린지는 `no_speech`를 기술 오류가 아닌 완료 결과로 처리한다. transcript·verdict·correctedAnswer·feedback은 null이고, `aiResult`와 attempt snapshot의 referenceAnswer는 유지한다. 잘못된 null 조합은 Callback에서 거절한다. [파서](../../src/main/java/web/tosunsaeng/domain/challenge/ChallengeCallback.java), [상태 전이](../../src/main/java/web/tosunsaeng/domain/challenge/ChallengeCallbackService.java), [응답 조립](../../src/main/java/web/tosunsaeng/domain/challenge/ChallengeViews.java), [계약 테스트](../../src/test/java/web/tosunsaeng/domain/challenge/ChallengeContractTest.java).

**활용:** “외부 AI의 무응답과 장애를 별도 도메인 결과로 설계하고 프론트 null 계약을 맞춘 경험.” 모의고사에 같은 enum·계약이 있었다고 소급해서 쓰지 않는다. Challenge는 기본 OFF이며 배포 전 조건은 [rollout](TEN_SECOND_CHALLENGE_ROLLOUT.md)을 따른다.

### 5.5 모바일 피드백 축약: 작은 AI 변경의 계약 파급

**[회고 사실]** 모바일에서 긴 피드백의 중복 설명을 줄이고 강점·약점을 최대 5개로 정리했다. AI의 작은 출력 변경도 백엔드·앱의 수정이 필요했다고 두 회고에서 설명한다. [7월 회고](https://velog.io/@jinjinjara1022/아이디어에서-첫-사용자까지-토선생-개발-7월-회고), [8월 회고](https://velog.io/@jinjinjara1022/일단-되게에서-제대로-되게로-토선생-개발-8월-회고).

**[구현 확인·한계]** 현재 백엔드의 요청·응답 DTO에 strengths/weaknesses 목록과 결과 변환 경로가 있다. 이 사실만으로 백엔드가 최대 5개를 강제하거나 당시 변경을 직접 수행했다고 확인할 수 없다. [요청 DTO](../../src/main/java/web/tosunsaeng/domain/exams/dto/ExamRequestDTO.java), [응답 DTO](../../src/main/java/web/tosunsaeng/domain/exams/dto/ExamResponseDTO.java), [변환](../../src/main/java/web/tosunsaeng/domain/exams/converter/ExamConverter.java).

**활용:** API·AI Callback의 nullable/목록/필드 의미 합의, 저장 후 조회 일관성, reader-first 배포·계약 테스트 같은 협업 소재다. 실제 참여 PR·fixture가 있는 항목만 본인 성과로 선택한다.

### 5.6 사전 생성 콘텐츠와 Part 4 표: 품질 검수와 전달 계약은 다르다

**[회고 사실]** 8월에 모의고사 콘텐츠 100세트를 만들고 평가 조건·metadata를 사전에 생성했다. Part 4는 표·질문의 부자연스러운 조합을 줄이기 위해 슬롯·템플릿 기반으로 바꿨다. Part 1 모범답안 TTS 품질도 별도로 실험했다. [8월 회고](https://velog.io/@jinjinjara1022/일단-되게에서-제대로-되게로-토선생-개발-8월-회고).

**[구현 확인]** 백엔드는 catalog를 검증·배정하고 질문·tableContext를 API로 전달하며, Part 4 전용 결과 변환에서도 질문 text를 유지한다. 모범답안 음성은 제출·채점 조건에 맞춰 노출하도록 테스트가 있다. [catalog](../../src/main/java/web/tosunsaeng/domain/exams/application/MockExamCatalogService.java), [변환](../../src/main/java/web/tosunsaeng/domain/exams/converter/ExamConverter.java), [모범답안 테스트](../../src/test/java/web/tosunsaeng/domain/exams/application/ExamQuestionModelAnswerTest.java). 실제 결함 수정은 사례집 TS-09·10.

**활용:** “AI가 만든 콘텐츠를 실제 응시·결과 화면에서 일관되게 제공하는 백엔드.” 콘텐츠 의미의 정확성·STT metadata 주입·TTS 모델 선택은 AI 책임과 분리한다. 현재 catalog 검사가 전체 Q1~Q11·음성·표 의미를 완전 검수한다고 표현하지 않는다.

### 5.7 모델 교체와 비용: 단가가 아니라 완료된 시험당 비용

**[회고 사실]** 7월에는 예상보다 몇 배 높은 비용을 경험한 뒤 외부 서비스·모델 구성과 처리 단계를 검토해 비용을 낮췄다고 설명한다. 정확한 전후 금액·절감률은 없다. 8월에는 자체 GPU 모델의 품질·지연·동시성을 실험했지만 운영 전환 완료로 쓰지는 않았다. [7월 회고](https://velog.io/@jinjinjara1022/아이디어에서-첫-사용자까지-토선생-개발-7월-회고), [8월 회고](https://velog.io/@jinjinjara1022/일단-되게에서-제대로-되게로-토선생-개발-8월-회고).

**[추론] 백엔드 연결:** 요청 단가가 낮아도 느린 접수·채점, repair 증가, timeout 뒤 중복 실행이 늘면 완료된 시험당 비용이 높아질 수 있다. 완료 문항 skip·멱등 처리·실패 분류는 비용 관점에서도 설명할 수 있지만 절감률은 실측해야 한다. [재시도·멱등 처리](../../src/main/java/web/tosunsaeng/domain/exams/application/ExamGradingService.java), [AI 전송](../../src/main/java/web/tosunsaeng/domain/exams/application/GradingDispatchService.java).

**[제안] 측정 후보:** 시험당 총 외부 호출 수·repair 수·성공 완료율·종단 대기시간 P95/P99·완료 시험당 비용. 모델 교체 전후에 결과 형식·언어·실패율도 함께 비교한다. MSA나 비동기화만으로 무조건 처리량이 늘었다고 하지 않는다.

### 5.8 구조화 로그에서 사용자 흐름 관측으로

**[회고 사실]** 7월에는 로그·코드를 따라 오류를 찾았고, 9월에는 여러 사용자가 같은 문항에서 멈추는 패턴이 장애 신호였다. 글 자체는 자동 funnel 경보를 구현했다고 말하지 않는다. [7월 회고](https://velog.io/@jinjinjara1022/아이디어에서-첫-사용자까지-토선생-개발-7월-회고), [장애 회고](https://velog.io/@jinjinjara1022/토선생-개발-일지-01-멈춰버린-서비스).

**[구현 확인]** 현재 요청 상관관계와 비동기 MDC 전달, 채점 상태 event 로그를 기존 포트폴리오의 구조화 로그 사례와 연결할 수 있다. [요청 필터](../../src/main/java/web/tosunsaeng/global/logging/RequestCorrelationFilter.java), [비동기 전파](../../src/main/java/web/tosunsaeng/global/logging/MdcTaskDecorator.java), [채점 로그](../../src/main/java/web/tosunsaeng/domain/exams/application/ExamGradingService.java).

**[제안]** 다음 개선은 서버 5xx뿐 아니라 시험 시작→문항 진행→제출→결과 조회의 중단 지점을 관측하는 것이다. 개인정보·원문·Presigned URL을 로그에 남기거나 사용자/시험 식별자를 metric tag로 넣지 않는 경계가 필요하다. 기존 구조화 로그 적용과 아직 없는 제품 경보를 한 성과로 합치지 않는다.

### 5.9 웹 검증에서 앱 출시까지의 제품·협업 경험

**[회고 사실]** 7월 빠른 웹 검증에서 8월 24일 iOS 앱 출시로 이어졌고, 실제 전체 응시 이용자가 생겼다. 프론트·백엔드·AI의 역할 분담 속에서 기능 필요성과 변경 영향을 협의했다고 설명한다. [7월 회고](https://velog.io/@jinjinjara1022/아이디어에서-첫-사용자까지-토선생-개발-7월-회고), [8월 회고](https://velog.io/@jinjinjara1022/일단-되게에서-제대로-되게로-토선생-개발-8월-회고).

### 6.4 이번 변경·검증과 남은 작업

- 변경: 이 보강 문서, 기존 사례집 TS-23·24 및 총 24개 후보 표, 기존 포트폴리오의 선택 안내, CURRENT_STATE와 WORKLOG EOF 기록.
- 확인: 원문 3편 본문 읽기, 현재 시험지 배정·S3 URL 생성·catalog·DTO·retry·Challenge no-speech 코드와 관련 테스트 대조, 로컬 링크·지정 행 및 `git diff --check` 검사.
- 애플리케이션 코드를 변경하지 않아 Gradle 테스트는 실행하지 않았다. 테스트 파일을 읽은 것과 테스트 실행 성공은 구분한다.
- 공개 API·DTO·BaseResponse·AI Callback·retryCount·S3/Redis 계약과 웹 POC·AWS·운영 DB는 변경하지 않았다. 배포할 runtime 변경도 없다.
- 기존 사용자 변경을 보존하며 이번 작업은 위 5개 문서 범위다. 본인 기여·당시 복구 결과를 확인한 뒤 포트폴리오 본문 사례를 선택한다. 장애율·비용·응답시간의 전후 개선 수치는 추가 실측이 필요하다.
