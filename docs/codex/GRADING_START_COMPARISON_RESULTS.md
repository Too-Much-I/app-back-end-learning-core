# 문항별 선행 채점 ↔ 11문항 종료 후 채점 비교

실행일: 2026-09-08. 같은 앱 백엔드와 모의 AI를 사용하는 **채점 시작 시점 대조 실험**이다. 실제 AI 비용/품질, 공식 시험 전체 진행 또는 운영 성능 측정이 아니다. 관련 TMI-25는 기존 채점 구현 배경이며 신규 Jira 변경 없음.

## 1. 5줄 결론

1. **실측**: 24개 실행에서 완주 대상48시험 모두 완료, 의도적 중단12시험을 별도 관찰했다. 588submit·48Summary, 제출/Callback/관찰 오류0건이다. [원시 결과](measurements/grading-schedule-2026-09-08.json)
2. **실측**: worker4·6시험 중첩의 종료 후 대기 p95 중앙값은 종료후21.90초→문항별3.42초로84.4% 감소했다. [집계](measurements/grading-schedule-2026-09-08.summary.json)
3. **실측**: 같은 중첩 조건의 실행 가능 대기 queue 최대값은56→7개였다. 문항별 군은 각 시험 종료 시 앞선10문항이 완료돼 있었다. [작업 시각·sample](measurements/grading-schedule-2026-09-08.json)
4. **실측**: worker16·단일 시험은 종료후2.80초/문항별2.82초로 의미 있는 단축이 관측되지 않았다. Q5 중단6시험/군의 모의 문항 연산 시작은 문항별30회/종료후0회다. [집계](measurements/grading-schedule-2026-09-08.summary.json)
5. **판단**: 제한된 자원에서 선행 채점의 대기 시간 효과를 지지하지만 비용 절감·실제 시험 대기 시간 개선율은 아니다. 20배 압축 모델이고 종료 후 군도 병렬 실행한다. [조건/한계](../../scripts/perf/README.md)

## 2. 반드시 읽어야 하는 내용

### 무엇을 비교했는가

| 항목 | 문항별 시작 | 11문항 종료 후 시작 |
| --- | --- | --- |
| submit·모의 AI 접수 | 각 문항 준비 시 동일하게 전송, 접수50ms | 동일 |
| 채점 실행 자격 | 문항 접수 후 즉시 | 종료 시점 및11문항 접수를 모두 확인한 뒤 |
| 실제 실행 | 공통 FIFO 동시성 제한 안에서 실행 | 같은 제한 안에서 병렬 실행 가능 |
| 문항별 연산량·결과 | 같은 모의 지연/점수 | 동일 |
| 최종 완료 | 모든 문항 결과와 Summary 준비 후 | 동일 |

양군 모두 비동기 접수다. 이전 동기/비동기 실험과 달리 백엔드가 AI 채점 완료까지 HTTP를 기다리게 하지 않는다. 이번 종료 후 방식은 실험 AI 내부의 작업 보류 gate로 구현했다. 제품의 신규 완료 API·일괄 submit·일괄 업로드·11문항을 하나로 묶은 LLM 요청을 구현한 결과가 아니다.

### 종료 후 대기 시간 결과

| 조건 | 군별 완주 시험 수(3회 합계) | 종료 후 시작 | 문항별 시작 | 관측 차이 |
| --- | ---: | ---: | ---: | --- |
| 단일 시험·worker4 | 3 | 5.444초 | 2.843초 | 47.8% 감소 |
| 6시험 중첩·worker4 | 18 | 21.896초 | 3.424초 | 84.4% 감소 |
| 단일 시험·worker16 | 3 | 2.801초 | 2.821초 | 단축 없음, 약20ms 차이 |

시간은3회별 p95의 중앙값이다. 단일 시험에서는 각 회차 표본이1개라 ‘단일 대기 시간3회의 중앙값’과 같다. 6시험 회차의 nearest-rank p95도 최대값이므로 운영 tail 성능으로 확대하지 않는다. 최종 submit **성공 응답 이후**의 대기 p95 중앙값으로 측정해도 단일 worker4는5.359→2.763초, 6시험 worker4는21.814→3.341초로 같은 방향이다.

완주 군에서는 양쪽 모두24시험·문항264회·Summary24회로 작업량이 같았다. 문항별 방식은 시험 종료 시10문항이 이미 완료됐고, 마지막 Q11과 Summary를 기다렸다. 종료 후 방식은 같은 작업량을 뒤늦게 시작했다. **AI 연산 자체가 빨라진 것이 아니다.**

### 부하 집중과 중도 포기

| 지표 | 종료 후 시작 | 문항별 시작 |
| --- | ---: | ---: |
| 6시험·worker4: 실행 가능 대기 queue 최대 | 56개 | 7개 |
| 6시험·worker4: queue 대기 p95 중앙값 | 17.873초 | 2.159초 |
| 단일 시험·worker16: 최대 사용 슬롯 | 11개 | 2개 |
| Q5 중단6시험/군: AI 문항 HTTP 접수 | 30회 | 30회 |
| Q5 중단6시험/군: 모의 문항 연산 시작 | 0회 | 30회 |

최대 queue/슬롯 값은 해당3회에서 모두 동일했다. worker16 조건에서 종료 후 군도11문항을 한꺼번에 실행할 수 있었고, 가장 긴 문항 지연을 Q11과 동일하게 설정했으므로 마지막 결과 대기 시간은 거의 같았다. 문항별 군은 더 낮은 순간 동시 실행으로 같은 정도의 최종 대기를 달성했지만, 총CPU/운영 비용을 측정한 것은 아니다.

중단 시 문항별 군은 시험당3문항 완료·4문항 시작 상태였고, 이미 제출한 Q5까지 처리가 계속되어 최종30회 연산이 실행됐다(중단 전에24회 시작, 중단 후12개 Callback 완료). 종료 후 군의30문항은 모의 AI에 접수됐지만 실행되지 않고 보류됐다. 이 보류 데이터는 실험 상태/컨테이너 종료와 함께 정리됐으며 영속 작업 정리·운영 취소 정책은 구현하지 않았다.

### 보고서용 정리

**문제**: 시험 종료 후11문항의 채점을 시작하는 대안은 응시 시간을 채점에 활용하지 못하고, 여러 시험이 비슷한 시점에 종료될 때 채점 작업이 집중될 수 있다.

**조치 — 현재 설계**: 각 문항의 답변을 제출하면 비동기 채점을 시작하고, 사용자는 채점을 기다리지 않고 다음 문항을 진행하도록 구성한다. 필수 문항 결과가 모두 준비된 이후 전체 요약을 생성하여, 문항별 선행 처리와 시험 전체 완료 조건을 분리한다. 이번 작업에서는 기존 문항별 구현을 변경하지 않고 종료 후 대안과 비교 검증했다.

**결과**: 같은 앱 백엔드와 모의 AI의 압축 시간표 실험에서, 6시험·4개 처리 슬롯 조건의 시험 종료 후 대기 p95 중앙값이 종료 후 방식21.90초 대비 문항별 방식3.42초로84.4% 낮았다. 실행 가능 대기 queue 최대값은56개 대비7개였고 완주 대상48시험은 모두 완료됐다. 충분한 병렬 자원을 둔 단일 시험에서는 두 방식 모두 약2.8초로 차이가 거의 없었다.

**남은 것**: 실제 앱 시간표와 AI latency·동시성으로 재검증하고, 중도 포기 비율 및 생성된 부분 결과의 재사용 가치를 함께 확인해야 한다. 이 수치는 운영 전후 측정이나 실제 비용 절감률이 아니다.

### 측정 지표

- 주지표: 마지막 답변 준비 및 최종 submit 시작 직전부터, status COMPLETED·Summary의11문항 결과·모든 문항/Summary Callback ACK를 확인할 때까지의 시간.
- 보조: 최종 submit 성공 응답 이후의 대기 시간, 종료 시점에 완료된 문항 수, 실행 중/대기/보류 작업 수, 요청·Callback 오류, 모의 연산 시작 수.
- 대기 queue는 실행 자격을 얻었지만 worker가 없는 작업이다. 시험 종료 전 보류 작업과 별개이며, raw sample의 `held`로 함께 기록한다.
- 중도 포기는 Q5 submit 직후 나머지 답변을 보내지 않는 조건이다. 진행 중/대기 중 작업을 취소하지 않는다. 결과가 없는 중도 포기 시험을 장애 실패로 세지 않는다.

## 3. 결정해야 하는 사항

- 결과 대기 시간과 중도 포기 시 선행 채점량을 함께 보고 현재 문항별 설계의 장단점을 판단한다. 완주한 동일 답변의 AI 연산 횟수 감소와 혼동하지 않는다.
- 종료 후 방식은 이번에 만든 비교 대안이지 확인된 과거 운영 구현이 아니다. 보고서에는 ‘기존 일괄 채점을 문항별로 전환했다’가 아니라 ‘문항별 선행 채점 설계의 효과를 종료 후 대안과 비교했다’고 쓴다.
- 실제 운영 개선율이 필요하면 배포 앱의 답변 준비/업로드 시각과 파트별 AI latency·동시성·rate limit을 확보한 뒤 실제 시간 축으로 검증한다.
- 제품을 종료 후 방식으로 전환하려면 접수 보존·보류 작업 TTL·시험 중단/재개·재시작 복구·현재 Job timeout과의 호환성을 별도 설계해야 한다. 이번 실행은 그런 제품 변경 승인이 아니다.

## 4. 주요 위험과 미확인 사항

1. **가정 시간표**: 문항별 준비·응답을 본뜬618초를20배 압축해30.9초로 실행한다. 공식 전체 시험 시간이나 실제 앱 로그 기반 시간표가 아니다. Directions·질문 음성 길이·마이크·기기 처리·업로드는 제외했다.
2. **시간 축 한계**: 모의 문항 연산0.6~2.2초, Summary0.3초는 고정 가정이다. HTTP·Mongo·Polling200ms는 축소하지 않으므로 결과를20배 곱해 실제 시험 지연으로 환산할 수 없다.
3. **자원**: worker4/16은 민감도 확인용 가정값이지 운영 AI worker 수가 아니다. 문항·Summary·Callback ACK가 같은 슬롯을 사용한다. Node timer는 실제 CPU/GPU/외부 API 연산이 아니다.
4. **전체 배포 제외**: 실제 Spring MVC/서비스/Mongo repository와 격리 Mongo/Redis를 쓰지만 비교용 수동 bean 구성이다. 전체 security/AOP wiring, JWT·Identity·Billing·S3 업로드·실제 AI·모바일을 검증하지 않는다.
5. **CPU**: JVM heap512MiB·ActiveProcessorCount2·Tomcat20 설정은 같으나 JVM CPU hard isolation은 아니다. Mongo CPU1/512MiB, Redis CPU0.5/128MiB의 컨테이너 제한과 구분한다.
6. **표본**: 짧은 유한 cohort를3회 반복한다. 단일 시험 조건의 회차별 p95는 한 표본 자체다. 6시험 조건도 각 회차 p95가 최대값이므로 운영 tail·신뢰구간·최대 동시 사용자 수로 일반화하지 않는다.
7. **중도 포기 비용**: 측정한 것은 모의 연산 시작/완료 횟수다. 이미 생성된 부분 결과의 가치·재사용·실제 유료 비용·업로드/저장 비용·취소 정책은 평가하지 않는다.
8. **장애 미주입**: provider rate limit·재시도·네트워크 장애·영속 queue·프로세스 재시작은 이번 비교에 없다. 제출/Callback 오류0이어도 운영 무장애라는 뜻은 아니다.

## 5. 현재 작업과 직접 관련된 설명

### 변경과 계약

- **구현 사실**: 기존 [submit 서비스](../../src/main/java/web/tosunsaeng/domain/exams/application/ExamServiceImpl.java)와 [문항 Job 처리](../../src/main/java/web/tosunsaeng/domain/exams/application/ExamGradingService.java)가 문항 단위 전송을 수행한다. 이번에는 그 제품 코드를 변경하지 않고 모의 AI의 시작 조건만 달리했다.
- [새 실행기](../../scripts/perf/run-grading-schedule.mjs), [시간표·gate·pool](../../scripts/perf/grading-schedule-model.mjs), [단위 테스트](../../scripts/perf/grading-schedule-model.test.mjs), [집계/검증기](../../scripts/perf/summarize-grading-schedule.mjs)를 추가했다.
- [비교 빌드](../../scripts/perf/comparison.init.gradle)에 앱만 준비하는 `prepareAppComparison`을 추가했다. 이번 실험은 웹 소스를 조회·컴파일·변경하지 않는다. 기존 Java 비교 실행기를 그대로 재사용한다.
- 공개 API/DTO/BaseResponse·retryCount·AI user_id=examId·Callback JSON·S3/Redis/Billing 계약, 제품 runtime과 운영 설정은 변경하지 않는다. 보류 gate는 모의 AI 안에만 존재한다.
- 기존 dirty AGENTS/runtime/문서/이전 테스트는 보존한다. 이번 범위 밖 제품 파일은 수정하지 않는다. 실험 도구/문서는 배포 불필요하며 운영 반영을 원하면 별도 실제 환경 검증이 필요하다.

### 검증

- `./gradlew clean test -I scripts/perf/comparison.init.gradle prepareAppComparison`: 일반 Java543개 통과, failures/errors/skipped0. XML81개 합계를 확인했다. 최초 sandbox Gradle cache lock 거부 후 승인된 실행으로 완료했다.
- `node --test scripts/perf/grading-schedule-model.test.mjs`: 시간표·즉시/종료 gate·중단·FIFO 동시성·통계6개 통과.
- smoke는 양군의 완주·중단 HTTP 경로를 확인했다. 본 실험과 집계하지 않는다. sandbox의 loopback listen 거부 뒤 승인된 실행으로 수행했다.
- 본 실험exit0, 집계기의24행/군별3반복/문항 누락·중복/실행 시작 gate/처리 시간/worker 한도/완료·오류 수 검증이 통과했다. 실행 시작 시 기록한5개 소스 SHA-256은 종료 후 현재 파일과 모두 일치했다. Node syntax와 문서 whitespace/링크를 확인했다.
- Java 종료 hook이 실험 Mongo/Redis를 정리했고, 승인된 읽기 전용 ps 확인에서 실험 Java/Node 잔존이 없었다. main/smoke에서 사용한 테스트 데이터는 임시 환경이며 원시/집계 JSON은 보존했다. 실제 AWS/Atlas/AI/Sentry나 사용자 음성은 사용하지 않았다.
- `clean`으로 기존 build 로그/임시 classpath/테스트 보고서는 재생성됐다. 이전 비교 원시/집계 JSON은 `docs/codex/measurements/`에 보존했다. 이번 Mongo는 실행기 내 격리 DB이며 `mongoIntegrationTest` task를 새로 실행한 것은 아니다.
