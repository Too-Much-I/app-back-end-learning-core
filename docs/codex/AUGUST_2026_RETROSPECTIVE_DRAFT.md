# 토선생 개발 8월 회고 — 앱 출시와 첫 사용자

8월은 토선생을 앱으로 출시하고, 처음으로 iOS 사용자를 받아본 달이었다. Learning Core와 Identity를 중심으로 기능을 추가하고 흐름을 정리했지만, 이번 달을 돌아보면 코드만큼이나 출시를 준비하며 겪었던 일들이 기억에 남는다.

앱이 실제로 검색되고, DB에 사용자가 들어오는 모습을 처음 확인했다. 그때부터 내가 만들고 있는 기능이 누군가의 시간과 노력이 담기는 서비스라는 점이 더 실감 났다.

## 생각보다 오래 걸렸던 Google 출시 준비

출시 과정에서 예상보다 어려웠던 부분은 Google이었다. 출시 자체에도 절차가 많았지만, 검토가 오래 걸려 준비한 앱을 바로 사용자에게 전달할 수 없었다.

개발자 계정은 팀원 명의로 준비했다. 관련 서류를 제출하는 과정도 있었는데, 제출한 서류가 리젝되면서 어려움을 겪었다. 코드를 고치고 테스트하면 확인할 수 있는 개발 문제와 달리, 서류와 검토 과정은 우리가 작업을 더 한다고 곧바로 끝나는 일이 아니었다.

기능 개발 일정은 생각하고 있었지만, 계정 준비와 서류 제출, 검토에 필요한 시간까지 충분히 고려하지는 못했다. 이번에 직접 겪고 나니 출시 준비도 개발과 함께 시작해야 하는 작업이라는 생각이 들었다. 다음에는 앱을 다 만든 뒤 준비하기보다, 미리 진행할 수 있는 절차부터 확인하고 시작하고 싶다.

## 앱이 검색되고, 사용자가 들어왔다

반면 Apple은 생각보다 빠르게 진행돼서 신기했다. 8월 24일에는 iOS 앱을 출시했고, 처음으로 iOS에서 사용자를 받아봤다.

앱을 검색했을 때 우리가 만든 앱이 실제로 나오는 게 정말 신기했다. 그동안 개발하면서 보던 앱이 이제는 다른 사람도 검색하고 설치할 수 있는 앱이 된 것이다.

DB를 확인했을 때도 사람들이 들어오고 있었다. 내가 테스트하면서 만든 데이터가 아니라, 실제로 서비스를 사용하는 사람들의 기록이 생기고 있다는 사실이 크게 다가왔다. 앱을 출시했다는 말보다 그 모습을 직접 봤을 때 훨씬 더 실감이 났다.

## Learning Core: 사용자의 20분이 결과로 이어지도록

Learning Core에서는 시험 이력과 문항별 재답변 조회, 채점 완료 알림을 추가했다. Part 4 결과에서 질문 문장이 빠지는 문제와 재답변 점수가 최초 시험의 파트 점수에 함께 더해지는 오류도 수정했다.

그중에서도 신경을 많이 쓴 부분은 채점 재시도와 복구였다. 채점이 AI 서버에서 이뤄지다 보니, 답변을 제출했다고 해서 점수와 피드백이 반드시 정상적으로 돌아오는 것은 아니었다. 결과가 누락되거나 종합 피드백이 비어 있는 경우까지 고려해야 했다.

사용자는 시험을 보기 위해 약 20분 동안 시간을 들이고 답변한다. 그런데 사용자의 잘못도 아닌 처리 문제 때문에 점수와 피드백을 보지 못한다면 안 된다고 생각했다. 이미 들인 노력을 생각하면, 오류를 보여주는 데서 끝내기보다 결과를 받을 수 있도록 복구하는 흐름이 필요했다.

종합 피드백이 비어 있는데도 완료로 처리할 수 있던 흐름을 수정하고, 실패한 부분을 다시 처리할 수 있도록 보완했다. 이미 완료된 문항까지 다시 요청하지 않고, 종합 피드백이나 누락된 문항처럼 필요한 부분만 복구하도록 했다.

재시도를 추가하면서는 응답 순서도 고려해야 했다. 이전 요청의 응답이 늦게 도착할 수 있기 때문에, 새 재시도의 상태나 결과에 영향을 주지 않도록 요청을 구분했다. 재시도 버튼 하나를 제공하는 것 뒤에도 중복 처리와 늦은 응답, 실제 결과 저장 여부를 함께 다뤄야 했다.

이 작업을 하면서 시험 시작과 제출뿐 아니라, 사용자가 점수와 피드백을 확인하는 순간까지가 하나의 흐름이라는 생각이 더 분명해졌다.

## Identity: 회원이 되어도 학습이 이어지도록

Identity에서도 비슷한 고민을 했다. Guest로 서비스를 사용하던 사람이 회원이 됐을 때, 그동안의 기록을 어떻게 이어갈 것인지가 중요했다.

Guest가 처음 회원으로 전환되는 경우와 이미 존재하는 회원 계정으로 합쳐지는 경우는 서로 달랐다. 처음 회원이 되는 경우에는 기존 사용자 식별자를 유지하는 승격 흐름을 만들고, 기존 회원으로 합쳐지는 경우에는 source와 target을 구분하는 계정 통합 흐름을 준비했다.

채점 복구에서 사용자의 시험 시간을 지키고 싶었던 것처럼, 계정이 바뀌는 과정에서도 이미 쌓은 기록이 잘 이어질 수 있도록 신경을 많이 썼다. 로그인에 성공하는지만 확인하는 것으로는 부족했고, 어떤 사용자로 전환되는지와 기존 기록을 어떤 기준으로 연결할지도 고려해야 했다.

계정을 합칠 때는 권한 처리도 중요했다. 이전 Guest의 Token을 통합 대상 회원의 권한으로 그대로 사용할 수 없도록 경계를 두고, 통합 이벤트를 다른 서버에 전달할 기반을 마련했다. 8월에는 Identity의 승격·통합 흐름을 구현하고, Learning Core의 학습 기록 이전으로 이어질 계약과 후속 작업을 정리했다.

이 밖에도 동의 관리와 탈퇴 기능을 보완했다. 가입과 로그인뿐 아니라 중단, 탈퇴, 재가입까지 생각하면서 사용자 계정을 다루는 범위가 생각보다 넓다는 것을 느꼈다.

## 추가로 만든 기반과 다음에 바꾸고 싶은 점

Learning Core와 Identity 외에도 Billing 서버를 만들기 시작했다. 전화번호 기준 무료 모의고사 응시권과 시험 생성의 예약 처리를 구현하며, 중간 실패나 재요청이 생겨도 중복 차감되지 않도록 연결했다. 웹 백엔드에서는 블로그 조회수와 Part 4 표 데이터 전달도 보완했다.

8월에 가장 아쉬웠던 점은 출시 준비를 더 일찍 시작하지 못했다는 것이다. 특히 Google의 긴 검토와 서류 리젝을 겪으면서, 개발 완료 시점만으로 출시 일정을 잡기 어렵다는 걸 배웠다. 다음에는 계정과 서류 준비, 플랫폼별 절차를 개발과 병행하고 싶다.

그래도 앱이 검색되고 실제 사용자가 들어오는 모습을 본 경험은 오래 기억에 남을 것 같다. 사용자가 약 20분 동안 본 시험이 점수와 피드백으로 이어지고, Guest에서 회원이 된 뒤에도 학습이 이어질 수 있도록 만드는 것. 앞으로도 그런 흐름을 신경 쓰면서 서비스를 다듬어가고 싶다.
